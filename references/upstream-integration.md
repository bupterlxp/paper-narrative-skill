## 规则如何落地

| 上游思路 | 整合后的规则 | 原因与落点 |
|---|---|---|
| 围绕最值得发表的价值组织论文 | 选最有证据的贡献，先说动作、结果和意义 | [六大范式](narrative-framework.md) 负责定位，[编辑规则](anti-defensive-writing.md) 负责成稿 |
| 不写项目总结和实验流水账 | 按论证顺序组织，删无关开发历史 | 保留影响比较有效性的选择过程；事后筛选不能当普通流水账删掉 |
| 明确说出优势，控制主张范围 | 直接陈述具体收益及成立条件 | 无需全面领先；有效权衡、理论结果与负结果也有贡献 |
| 不主动示弱、禁用负面措辞 | 删除无依据的自我贬低；保留有信息的限制与不利结果 | 不采用 `only`、`may`、`underperforms` 等禁词表；见 [实例 3–5](../examples/before-after.md#3-有均值与波动直接报告保持判断尺度) |
| “打不过的维度，不设为比赛项目” | 可据真实需求重定位，保留原评价、选择依据和探索状态 | 新指标/子集未经独立确认不能写成确定优势；见 [实例 6](../examples/before-after.md#6-事后选择子集不补写一个效率故事) |
| 每个实验都有论证职责 | 同时纳入主效果、机制、约束价值、替代解释、失败边界与证伪 | 关键反例不能因为不利而移出论证 |
| 允许彻底重构故事 | 原主张不成立时据最强证据调整主线 | 只在用户要求重构或事实修正确有需要时改结构；最小编辑保持段序 |
| 结论强化记忆点 | 重申已建立的贡献，不引入新结果或笼统自我否定 | 必要假设和范围继续成立；按用户/会议要求写具体限制 |
| 精简版提示词的最小修改 | 按请求交付成稿，保留事实、符号、引用和作者口吻 | 小改稿不附完整诊断；正文、字数、语言约束优先 |

## 如何检验整合效果

[十组改写实例](../examples/before-after.md) 展示可交付文字；[检查场景](../evals/scenarios.md) 给出原始请求和可核对标准。检查重点是贡献是否更清楚、事实与主张是否对应、用户要求是否得到满足，不靠“删除了多少谨慎词”评分。

这些材料用于维护和人工核对，不构成论文录用率实验，也不代表已验证某模型在新输入上的表现。
